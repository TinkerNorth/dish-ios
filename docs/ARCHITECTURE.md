# Architecture

A map of the codebase aimed at people working in it. It says which primitive to
reach for, where the code goes, and what the layering rules are. The protocol
contract lives in `satellite/docs/contract.md`; the iOS-side mapping, almost
all of it not yet, is [`contract.md`](contract.md). The design tokens are in
[`../DESIGN.md`](../DESIGN.md); the shell's, the pages' and the kit's rules in
[`UI_CONTRACT.md`](UI_CONTRACT.md); the design handoff in
[`design/README.md`](design/README.md).

This is wave 1, the shell. The engine publishes real, empty facts, and the
sections below say which parts of the layering have code today and which are
the rules the next waves carry.

Data flows one way. A source of truth owns state, pure reducers derive from
it, the UI binds and renders it, and the UI sends commands back to the source.
The UI never owns domain state, and nothing below the `Dish` module imports
SwiftUI or UIKit.

## The prime directive: the engine is independent of the UI

You could delete `Sources/Dish/` and write a different front end (an App
Intents extension, a command-line harness) without touching a file under
`Sources/DishEngine/`, `Sources/DishKernel/` or `Sources/DishCore/`. That is
the test for every change, and the compiler runs it: the four modules are
SwiftPM targets whose dependency arrows point one way, and
`Tests/ArchitectureTests` pins which system frameworks each one may import.

```
        ┌──────────────────────────────────────────────────────────────┐
        │  Dish          SwiftUI projection: scene, shell, pages, kit    │
        │                binds state ▲             │ calls intents       │
        └────────────────────┼───────────────────────┼─────────────────┘
                             │                       ▼
        ┌────────────────────┴─────────────────────────────────────────┐
        │  DishEngine    stores · clock · seams · intents                │
        │                the composition root (AppModel)               │
        └────────────────────┬──────────────────────┬──────────────────┘
                             │ built on             │ built on
        ┌────────────────────┴──────────┐ ┌─────────┴──────────────────┐
        │  DishKernel                   │ │  DishCore                  │
        │  StateSource                  │ │  setup · wire · reducers   │
        │  (Foundation + Observation)   │ │  (Foundation + CryptoKit)  │
        └───────────────────────────────┘ └────────────────────────────┘
```

Beside the package sits a thin app target, `DishApp`, generated by XcodeGen
from `project.yml` into the committed `Dish.xcodeproj` (product `Dish.app`,
bundle id `com.tinkernorth.dish.ios`). `App/Sources/DishApp.swift` is the
`@main`: it declares the one app delegate, `OrientationLock` (SwiftUI takes a
delegate adaptor only from the `App` itself), and calls
`DishScene(orientation:)`; the Info.plist, the entitlements and the asset
catalog (icon, accent, launch background) live under `App/`. The project sits
at the repository root because Xcode resolves a local package at the project's
own directory.

## The module map

| Module | Role | Depends on | May import |
|---|---|---|---|
| `DishCore` | The pure core: the setup machine (`Setup/`), the protocol constants (`ProtocolConstants.swift`), the wire codecs and the session crypto (`Wire/`) and the policy reducers (`Reducers/`), ported from dish-mac under its names and pinned by the fleet's vectors. | nothing | Foundation, CryptoKit |
| `DishKernel` | The dataflow primitive `StateSource` (below) | nothing | Foundation, Observation |
| `DishEngine` | Everything that owns state or touches the platform: the preference stores (`Preferences/`), the minute clock (`Clock/`), the Local Network seam (`LocalNetwork/`), the recorded binding requests (`Setup/`), the facts the UI draws (`Models/`) and `AppModel`, the one composition root, with its intents by topic. Later `Network/` (sockets, REST, discovery) and the GameController bridge. | `DishCore`, `DishKernel` | Foundation, Observation, os, DishCore, DishKernel; never SwiftUI or UIKit |
| `Dish` | The SwiftUI library: `DishScene` and `OrientationLock` (the two `public` types), the navigation machine and its store, the shell, the pages, the setup cover and the dim, the kit, the mappers, the theme, the localized words and their catalog | `DishEngine`, `DishCore`, `DishKernel` | Foundation, Observation, SwiftUI, UIKit (only `UI/Theme.swift` and `DishScene.swift`), the three modules |

`ImportBoundariesTests` fails the build when a file imports outside its row
(`App/Sources` may import SwiftUI and `Dish` only); `PackageGraphTests` fails it
when a dependency points the wrong way, when a third-party package appears,
when a target lets a warning through, or when the scheme in `project.yml` does
not list every test target.

Inside the engine the folders are the contract: `Models/` is the value types
the UI binds, `Preferences/` the stores over `UserDefaults`, `Clock/` the
wall-clock fact, `LocalNetwork/` and `Setup/` the seams to what later waves
build, and `AppModel*.swift` the root and its intents. The engine's UI-facing
surface is `package`-visible; everything else stays `internal`, and the tests
reach it with `@testable import`. `public` is `DishScene` alone.

## The kernel primitive

One primitive lives in `Sources/DishKernel` today: the Swift form, on
Observation instead of Combine, of the set dish-android, dish-linux and
dish-windows share.

| You have... | Use |
|---|---|
| state owned from a socket, timer, cache or setting | `StateSource<S>`: a `@MainActor @Observable` final class that exposes `state` read-only, mutates through `setState` or `updateState`, and drops equal values |

`StateSource` is **held, not subclassed.** A store has one as a private
property and forwards `state`, so Observation tracks a read of the store
through the source it holds; an `@Observable` class cannot usefully be
inherited from, and a store that extended it would publish its own
implementation details. Every store in the engine is shaped the same way
(`OnboardingPreferenceStore`, `AppearancePreferenceStore`,
`DevicePreferenceStore`, `StreamingPreferenceStore`, `ClockSource`): the key is
a `static let`, `UserDefaults` is injected, the setter returns early on an
equal value and persists before it republishes.

The kernel's other four primitives (`Composer`, `Controller`, `Repository`,
`AsyncState`) are not ported; each has a row in
[`../Tests/PARITY.md`](../Tests/PARITY.md), and the wave that needs it ports it
with its tests. Until then a derived value is a computed property
(`AppModel.shellFacts`, which Observation tracks through the stores it reads)
and a request does not exist.

Two more conventions are classes written per feature. A **coordinator** owns
imperative, cross-cutting commands over several sources and re-exposes a
child's state by reference, never as a copy; there is none yet. A **gateway**
is an IO boundary with no domain state; the seams of this wave
(`LocalNetworkAccess`, `Ticker`) are protocols with one production
implementation each, so a test replaces them. A **reducer** is a pure free
function in `DishCore` for a `(state, event) -> result` decision.

## The composition root

`AppModel` (`Sources/DishEngine/AppModel.swift`) is a `@MainActor @Observable`
final class and the only place the engine's objects are made. The designated
initializer takes every collaborator, so a test builds one over fakes; the
convenience initializer takes a `UserDefaults` and builds the real set: the four
preference stores over those defaults, a `ClockSource` over a `TimerTicker`, a
`RecordedLocalNetworkAccess` and a `BindingRequests`.

`DishScene` is the composition root of the app layer. It makes `AppModel` and
`NavigationStore` once, as `@State`, hands the store the model's
`onboarding`, `startSetup` and `endSetup`, injects both with `.environment`,
passes down the two values only UIKit can give (`settingsURL`, from
`UIApplication.openSettingsURLString`, and `appVersion`, from the bundle),
drives `preferredColorScheme` from the appearance fact and sets the idle timer
from `idleTimerDisabled(facts:)`. It is the one file that reads
`UIApplication.shared`, `UserDefaults.standard` and `Bundle.main`;
`NoSuppressionsTests` pins that, and `ViewPurityTests` does not treat it as a
view.

What `AppModel` publishes today:

- `shellFacts`, a computed `ShellFacts` the mappers word: `controllers`,
  `attachedPads`, `paired`, `found`, `scanning` and `session` (all empty: no
  source exists yet), `localNetwork` (the seam's status, which stays `.unknown`),
  `preferences` (the stores' state), `now` (the clock) and `setup` (the walk,
  nil while the cover is down).
- the intents, in extensions by topic: `AppModel+Setup.swift` (`startSetup`,
  `endSetup`, `setupNext`, `setupBack`, `setupSkip`, `pickSetupInput`,
  `answerLocalNetwork`, `pickSetupDestination`, `setSetupEmulateAs`,
  `setSetupMotion`, `bindSetup`), `AppModel+Preferences.swift` (`setDeviceName`,
  `setKeepScreenOn`, `setDimAfter`, `setAppearance`) and `AppModel+Pages.swift`
  (`pageAppeared`, `pageDisappeared`). A view calls these and nothing else.

## Unidirectional flow: the rules

1. **One owner per piece of state.** It lives in exactly one source and is
   exposed read-only. Nobody else stores a copy. The setup walk lives in
   `AppModel`'s `setupSource`; the navigation state lives in `NavigationStore`.
2. **Derive, do not mutate.** Downstream values come from a pure transform: a
   mapper from facts to a view state.
3. **Effects as data, executed at the edge.** A reducer returns what to do; the
   model or the store does it. `reduceSetup` returns `SetupEffect`s that
   `AppModel+Setup` runs; `reduceNavigation` returns `NavigationEffect`s that
   `NavigationStore` runs.
4. **One publish, then rebuild.** The UI rebuilds from the snapshot; no
   per-field back channels that can miss a transition.
5. **Distinct-until-changed everywhere.** Every state value is `Equatable`,
   and `StateSource` drops an equal write.
6. **Commands flow the other way, explicitly.** The UI calls an intent on
   `AppModel`; the resulting state flows back out as a fact in `shellFacts`,
   which a page's mapper turns into its view state. A view holds no engine
   object: the scene hands its pages `AppModel` and `NavigationStore` and
   nothing else, and a page reaches everything through `ShellFacts`.
   `ViewPurityTests` enforces it, rule by rule
   ([UI_CONTRACT.md](UI_CONTRACT.md), "View purity").
7. **The engine vends data, the app vends words.** A fact is an enum or a
   number (`LinkHealth`, `ConnectionState.offline(lastSeen:)`, `DimDelay`);
   `L10n` is the one place a key becomes a word, and the String Catalog is the
   one place it is translated. The derivations between a fact and what a view
   draws (a row's text, a dot's colour, the "iPhone" a device name falls back
   to) are pure functions under `Sources/Dish/UI/Mappers`. A decision the fleet
   shares, such as the setup walk's, is a reducer in `DishCore`; the mapper
   only words its output. No `String` is built for display in `DishEngine`.
8. **A kit component reads no domain.** Anything under `Sources/Dish/UI/Kit`
   takes only its view state, tokens and closures; a host view beside the
   page maps the engine's value into that state and forwards the closures as
   intents. `ImportBoundariesTests` pins it: a kit file imports only SwiftUI
   and Foundation, observes no model and binds to none.
9. **Navigation is data.** `Sources/Dish/Navigation/NavigationMachine.swift` is
   a pure `reduceNavigation(state, event)` over the selected tab, each tab's
   pushed pages and the cover on screen; it returns its effects
   (`markWelcomeComplete`, `startSetup(entry)`, `endSetup`) as data and
   `NavigationStore` runs them and hands `TabView`, each `NavigationStack` and
   the `fullScreenCover` their bindings. See "Navigation" below.
10. **A page's lifecycle is an intent.** A page's `onAppear` and `onDisappear`
    forward `pageAppeared` and `pageDisappeared` to `AppModel`
    (`AppModel+Pages.swift`), which starts and stops what the page needs; today
    the Connections page runs the clock so an offline PC's "last seen" words
    stay current, and the view does nothing else there.

## Navigation

The machine is a pure function, `reduceNavigation(_:_:) -> NavigationStep`, over
`NavigationState` (the selected `Tab`, a `[Page]` per tab, the `Cover?`). Its
events and effects are the table in [UI_CONTRACT.md](UI_CONTRACT.md); the
shape is the dish-mac machine's, with the rail replaced by a tab bar and the
leave guard and the window gone.

- A tap on the tab already on screen pops it to its root, as iOS does.
- A page pushes onto the tab on screen; a pop the stack makes itself (the back
  button, a swipe) arrives as `pathChanged`, so the state follows the system.
- Setup and the dim are covers. Setup replaces whatever covered the tabs, the
  dim included; the dim rises only over the tabs, because the accessory that
  asks for it is not on screen under a cover.
- Leaving setup by any road, Skip, Bind or the system lowering the cover,
  lands on Controllers and completes the welcome, or it would rise again on the
  next launch. A cover the system lowers ends what it showed: setup as a skip,
  the dim as a wake.
- On a first run the store raises the setup cover before anything is drawn and
  starts the walk, so the tabs never flash.

`NavigationCoverageTests` keeps the map whole: every `Tab` and `Page` case has
its worded title in `ShellMappers.swift`, its `<Name>Page.swift`, its
`<Name>MappersTests.swift` and a branch of the shell's switch, and every
`Cover` case has its `<Name>Cover.swift` and a branch of the cover switch.

## The setup machine

The setup walk is `reduceSetup(state, event, localNetwork:)` in `DishCore`: a
pure function from a `SetupState` (the step, the draft, where the walk opened)
and a `SetupEvent` to the next state and a list of `SetupEffect`s. It is in the
core, not the engine, because it is a decision with no IO, and it is tested
there (`Tests/DishCoreTests/SetupMachineTests.swift`) with no mocks.

- The steps are `welcome`, `input`, `localNetworkPrimer`, `pickPC` and
  `review`. The primer and Pick your PC are both the Destination step: the
  primer stands in while the Local Network status is `.unknown`, and its
  Continue emits `.askLocalNetwork`; the answer moves to Pick your PC and emits
  `.scan` when allowed. iOS puts the question only once, so an earlier answer
  is the answer.
- A pick of the input moves on and seeds the draft (a seen pad emulates its own
  family, anything else an Xbox Wireless; motion follows what the pad carries).
- Review's Bind emits `.bind(draft)` then `.ended(.bound)`. Skip anywhere emits
  `.ended(.skipped)`. Back walks one step; there is none from the welcome, and
  none from Input when the walk opened there ("Add a controller").
- Nothing leaves the draft until Bind, and Bind is recorded in
  `BindingRequests`, not sent.

`AppModel+Setup` applies the machine to the model's `setupSource` and runs the
effects: `.askLocalNetwork` and `.scan` go to the `LocalNetworkAccess` seam,
`.bind` to `BindingRequests`, and `.ended` is the view's business (the cover
sends `navigation.send(.setupEnded(...))` itself, and the model only drops the
walk when `endSetup()` is called). The pure view-layer half is
`setupCoverState(facts:words:)` and the step mappers.

## Threading and the hot path

The pad side of the hot path is built (`Sources/DishEngine/Input/`); the
socket and the session are not. `GameControllerInput` hands each pad its own
serial `handlerQueue` before installing a handler; the handler samples the
extended gamepad into a `PadSample`, `wireReport` turns it into a
`GamepadReport`, and the pad's `PadFeed` drops a report that repeats the last
one, applies the dead zones from an atomic word, writes the inspector's
record under a seqlock and calls the `PadSink` of the route it took from its
mailbox. The feed is `Sendable` because every field is an atomic word or a
`let`, not because anything is promised past the compiler. The return paths
post to each pad's `FeedbackPad`, and `PadActuators`, an actor whose executor
is the `dish.feedback` queue, drives CoreHaptics, the light, the adaptive
triggers and the player index; a `GCController` is filed there by identity
and found in the framework's own list, so it never crosses isolations.
`LockLawTests`, in a `LOCK_STATS` build, holds the Input, Receive and
Feedback threads to no tracked lock. Everything else in the engine is
`@MainActor`.

These are the rules the bridge keeps and the wire will carry, taken from
dish-mac:

- Every controller event takes one path and takes no lock on it. A
  controller's handler runs on that controller's own serial queue, its
  `handlerQueue`, set before any handler is installed, so no event waits
  behind the main thread or another pad.
- On that path: no lock, no allocation, no main-actor hop, no `Task`, no
  `await`, no Observation. The report is sealed from a stack buffer and
  leaves through `sendto`, on a raw POSIX socket carrying `IP_TOS = 0xB8`
  (DSCP EF) and `SO_NOSIGPIPE`.
- The kernel is never on that path. `StateSource` is for state the UI reads;
  what the hot path shares with the main actor travels in atomic words and
  mailboxes.
- The main actor owns every published property. Handler installs are
  `nonisolated`, so the compiler refuses a handler that reaches for
  main-actor state.
- Return paths (rumble, the light bar) run the other way in one hop to a queue
  that owns the actuators.
- A mailbox or a direct send before a queue. The siblings carry a lock-free
  bounded queue of Vyukov's design (the satellite's log queue, the desktops'
  `MpscQueue` under the speaker playout, Android's `mpmc_ring` under the
  bridge, the speaker and the USB acks); dish-mac carries none, and neither
  does this client: no lane here has several producers feeding one consumer,
  and iOS has no pad speaker and no USB output lane without the Direct path.
  `Tests/PARITY.md` says when one would be ported and in which form.
- Some of the siblings' capabilities sit behind entitlements Apple grants on
  request: the multicast entitlement for the legacy discovery beacon, raw HID
  access for the Direct path. The hot path reaches every pad through
  GameController and every satellite through Bonjour until they are granted;
  `Tests/PARITY.md` lists them.

## How to add a feature

1. **Name the state.** A lifecycle takes a reducer in `DishCore` with an
   exhaustive test; a setting takes a store.
2. **Write the pure core first**, red then green, in `DishCore` or as a free
   function. No IO.
3. **Own it in a store** in the engine that holds a `StateSource`, or a
   coordinator method for a cross-cutting command. Feed world signals in;
   expose state out. A platform capability goes behind a protocol seam, with
   a recording or manual implementation for tests.
4. **Project it in `AppModel`** as a field of `ShellFacts` plus the intents,
   and build every state of the page: empty, loading, error and content, each
   through its mapper and shown in a `#Preview`.
5. **Localize at the edge.** A new word is an `L10n` property with its catalog
   entry and five translations; the engine gets a case, not a sentence, and the
   view gets the property, not a literal.
6. **Wire it once in `AppModel`**, the only composition root, and update
   [`../Tests/PARITY.md`](../Tests/PARITY.md) in the same change.

## Known limitations and not yet implemented

Each entry names the decided shape, so a change lands on it. The row-by-row
list, with where each lands, is [`../Tests/PARITY.md`](../Tests/PARITY.md).

- **Nothing talks to a PC.** No discovery, pairing, wire protocol or
  controller bridge; the engine's controllers, connections and session are
  empty. The Local Network denied state, the session accessory's Reconnect and
  the dim's only trigger are built and tested through their mappers and
  previews, and are unreachable at run time.
- **The recorded seams.** `RecordedLocalNetworkAccess` counts asks and scans and
  never answers, and `BindingRequests` keeps the drafts Bind asked for. Both are
  the shape the discovery and binding waves fill.
- **iOS gives apps no pad speaker.** The Review step's "Gets back" column
  never carries a speaker, because iOS offers apps no way to play into a
  controller.
- **A custom satellite glyph is not drawn.** An SF Symbol antenna stands in.

## Testing

- **The pure core is the contract.** The setup machine has a test for every
  step, event and branch, in `Tests/DishCoreTests`, with no mocks.
- **The kernel is tested as a kernel.** `Tests/DishKernelTests` pins
  `StateSource`'s distinct-until-changed rule.
- **The engine is tested against fakes it owns.** `Tests/DishEngineTests`
  drives the stores over a fresh `UserDefaults` (`TestDefaults`), the clock
  over a `ManualTicker`, and the intents over a model built with
  `RecordedLocalNetworkAccess` and `BindingRequests`.
- **The rules are tested.** `Tests/ArchitectureTests` reads the tree: import
  boundaries, the dependency graph, license headers, suppressions, mutable
  statics, the lint thresholds, the tool and workflow pins, the version
  mirrors, the catalog, the tokens, the view purity rules (`ViewPurityTests`)
  and the navigation's coverage (`NavigationCoverageTests`).
- **The app layer is tested where it decides.** `Tests/DishTests/Mappers`
  covers every page's mapper, one test per flow (empty, content, each
  variant), and `Tests/DishTests/Navigation` covers the machine and the store.
  What a test cannot say, how it looks, is a `#Preview` per state.
