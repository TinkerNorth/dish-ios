# Architecture

A map of the codebase aimed at people working in it. It says which primitive to
reach for, where the code goes, and what the layering rules are. The protocol
contract lives in `satellite/docs/contract.md`; the iOS-side mapping, row by
row with its files, is [`contract.md`](contract.md). The design tokens are in
[`../DESIGN.md`](../DESIGN.md); the shell's, the pages' and the kit's rules in
[`UI_CONTRACT.md`](UI_CONTRACT.md); the design handoff in
[`design/README.md`](design/README.md).

The shell, the controller bridge, the protocol core and the network engine
are built: the engine finds a Satellite over Bonjour, pairs with it both
ways, opens its session and streams a bound pad to it over the encrypted
data plane. The sections below say which parts of the layering have code and
which are the rules the next waves carry.

Data flows one way. A source of truth owns state, pure reducers derive from
it, the UI binds and renders it, and the UI sends commands back to the source.
The UI never owns domain state, and nothing below the `Dish` module imports
SwiftUI or UIKit.

## The prime directive: the engine is independent of the UI

You could delete `Sources/Dish/` and write a different front end (an App
Intents extension, a command-line harness) without touching a file under
`Sources/DishEngine/`, `Sources/DishKernel/` or `Sources/DishCore/`. That is
the test for every change, and the compiler runs it: the four modules are
SwiftPM targets whose dependency arrows point one way, and
`Tests/ArchitectureTests` pins which system frameworks each one may import.

```
        ┌──────────────────────────────────────────────────────────────┐
        │  Dish          SwiftUI projection: scene, shell, pages, kit    │
        │                binds state ▲             │ calls intents       │
        └────────────────────┼───────────────────────┼─────────────────┘
                             │                       ▼
        ┌────────────────────┴─────────────────────────────────────────┐
        │  DishEngine    stores · clock · seams · intents                │
        │                the composition root (AppModel)               │
        └────────────────────┬──────────────────────┬──────────────────┘
                             │ built on             │ built on
        ┌────────────────────┴──────────┐ ┌─────────┴──────────────────┐
        │  DishKernel                   │ │  DishCore                  │
        │  StateSource                  │ │  setup · wire · reducers   │
        │  (Foundation + Observation)   │ │  (Foundation + CryptoKit)  │
        └───────────────────────────────┘ └────────────────────────────┘
```

Beside the package sits a thin app target, `DishApp`, generated by XcodeGen
from `project.yml` into the committed `Dish.xcodeproj` (product `Dish.app`,
bundle id `com.tinkernorth.dish.ios`). `App/Sources/DishApp.swift` is the
`@main`: it declares the one app delegate, `OrientationLock` (SwiftUI takes a
delegate adaptor only from the `App` itself), and calls
`DishScene(orientation:)`; the Info.plist, the entitlements and the asset
catalog (icon, accent, launch background) live under `App/`. So do the App
Shortcuts (`App/Sources/DishShortcuts.swift`) and the two catalogs the
system reads the App Intents' words from (`App/Resources/Localizable.xcstrings`
and `AppShortcuts.xcstrings`): App Intents reads a provider and its words only
from the app's own target and bundle, and the intents it names are the
package's (`Sources/Dish/Intents/`). The project sits
at the repository root because Xcode resolves a local package at the project's
own directory.

## The kernel primitive

One primitive lives in `Sources/DishKernel` today: the Swift form, on
Observation instead of Combine, of the set dish-android, dish-linux and
dish-windows share.

| You have... | Use |
|---|---|
| state owned from a socket, timer, cache or setting | `StateSource<S>`: a `@MainActor @Observable` final class that exposes `state` read-only, mutates through `setState` or `updateState`, and drops equal values |

`StateSource` is **held, not subclassed.** A store has one as a private
property and forwards `state`, so Observation tracks a read of the store
through the source it holds; an `@Observable` class cannot usefully be
inherited from, and a store that extended it would publish its own
implementation details. Every store in the engine is shaped the same way
(`OnboardingPreferenceStore`, `AppearancePreferenceStore`,
`DevicePreferenceStore`, `StreamingPreferenceStore`, `ClockSource`): the key is
a `static let`, `UserDefaults` is injected, the setter returns early on an
equal value and persists before it republishes.

The kernel's other four primitives (`Composer`, `Controller`, `Repository`,
`AsyncState`) are not ported; each has a row in
[`../Tests/PARITY.md`](../Tests/PARITY.md), and the wave that needs it ports it
with its tests. Until then a derived value is a computed property
(`AppModel.shellFacts`, which Observation tracks through the stores it reads)
and a request does not exist.

Two more conventions are classes written per feature. A **coordinator** owns
imperative, cross-cutting commands over several sources and re-exposes a
child's state by reference, never as a copy. A **gateway** is an IO boundary
with no domain state. A **reducer** is a pure free function in `DishCore`
for a `(state, event) -> result` decision.

The network engine has these, under dish-mac's names:

| Object | Kind | What it does |
|---|---|---|
| `WifiConnectionManager` (`Network/WifiConnectionManager*.swift`) | coordinator | The pool of satellite sessions: connect, pair (path A in `+Pairing`, path B in `+Approval`), the session PUT and the re-key (`+Session`), the per-slot converge (`+Slots`), the scan (`+Discovery`), death, close-notify, reconcile and the backoff (`+Lifecycle`). `@Observable`; every decision it takes is a `DishCore` reducer's. |
| `WifiConnection` (`+Slots`, `+ReturnPaths`) | the per-satellite state the manager drives | The session's state machine, the alive tick, the slot table, the live client and the return-path routes. |
| `ConnectionHub` | coordinator | The rows the pages read, derived on each read from the manager's observable state, and the slot → connection binding table with its memory across restarts: one record per pad of one kind (`BindingMemoryStore`'s `wifi_binding_list` for a satellite, the Moonlight store's `moonlight_binding_list` for a host), written on bind, kept on release, dropped on unbind and Forget, and handed back by `takeDueStandingBindings` once per attachment of the pad. |
| `BindingMemoryStore`, `MotionBackendStatusStore` | stores | The satellite bindings kept across restarts, over the same `UserDefaults`; and each bound pad's motion word from its satellite's last apply, keyed by `SlotKey` (PC and pad), cleared with the binding. |
| `PairingAttempts` | store | Each satellite's pairing card, over a held `StateSource`. |
| `ConnectionStore`, `KeyStore`, `CertPins` | stores | The remembered satellites and the device id in `UserDefaults`, the pairing keys in the Keychain, the TOFU pins in a file of their own (the TLS delegate reads them off the main actor). |
| `HTTPClient`, `PairingClient`, `TofuPinningDelegate` | gateways | The REST control plane over `URLSession`, TOFU-pinned. |
| `SatelliteClient` (`+IO`, `+Streams`, `SendGate`, `ReceiveHandlers`) | gateway, and the hot path's sink | The UDP data plane: one POSIX socket, the session key, the counters, the replay guard, the heartbeat and the receive thread. It is the `PadSink` a bound pad's feed sends to. |
| `BonjourScan`, `MdnsBrowser`, `LocalNetworkProbe` | gateways | The `_satellite._udp` browse, and what it says about the Local Network permission. |

The Moonlight hosts have these, under dish-mac's names, in `Moonlight/`:

| Object | Kind | What it does |
|---|---|---|
| `MoonlightConnectionManager` (`+Pairing`, `+Probe`, `+Session`, `+Memory`, `+Forget`) | coordinator | The hosts: the `_nvstream._tcp` scan and the typed address, the five-phase PIN pairing, the probe that tells paired from trust lost from replaced, one session per host converged from what the bindings ask, the app pick, and forget. `@Observable`; it tells the model what happened through `onEvent` and that its pool or records moved through `onPoolChanged`. |
| `MoonlightConnection` | the per-host state the manager drives | The session reducer's state, the pads the host carries (`MoonlightPadLink`, the hot path's half) and the live control session with its clock. |
| `MoonlightHostStore`, `MoonlightIdentityStore` | stores | The remembered hosts, the remembered bindings and the client id in `UserDefaults` under the fleet's keys; the RSA identity and its self-signed certificate in the Keychain, minted once off the main actor. |
| `MoonlightGateway`, `MoonlightHttpTransport` | gateways | One `NWConnection` per request, mutual TLS with the identity, the host's certificate pinned on first use in `CertPins` and replaced by the one a pairing proves. |
| `MoonlightRtspClient`, `UdpControlTransport`, `MoonlightMediaPinger`, `MoonlightControlSession` | gateways | The RTSP handshake, the control socket, the pings that keep the media ports open, and the control stream: input sealed under AES-GCM and carried on the ENet client. |
| `MoonlightFeedbackRouter` | router | A host's rumble and light, folded per motor and gated by the switches, posted to the pad bound to the number it names. |

The manager's seams are protocols too: `MoonlightHostGateway`
(`ScriptedMoonlightGateway` in the tests), `MoonlightSessionEdges` (the live
sockets, or `FakeMoonlightEdges`) and the discovery closure.

The seams are protocols with one production implementation each, so a test
replaces them: `LocalNetworkAccess` (`BonjourLocalNetworkAccess`, the scan;
`RecordedLocalNetworkAccess` for tests), `Ticker`, `ControllerSource`,
`KeyStore` (`KeychainKeyStore`, `InMemoryKeyStore`) and the manager's
`DiscoveryPaths` (the live browse, or a scripted LAN). Two have theirs in the
scene, because only UIKit can fill them: `Pasteboard` (`SystemPasteboard`)
and `DeviceBattery` (`SystemDeviceBattery`, `UIDevice`'s level and charge
state), each `Inert` in a model built outside the scene.

## The composition root

`AppModel` (`Sources/DishEngine/AppModel.swift`) is a `@MainActor @Observable`
final class and the only place the engine's objects are made. The designated
initializer takes every collaborator, so a test builds one over fakes; the
convenience initializer takes a `UserDefaults` and builds the real set: the four
preference stores over those defaults, a `ClockSource` over a `TimerTicker`,
the pads (`ControllerStack` over `GameControllerInput`), the satellite pool
(`NetworkStack`: the manager over a `ConnectionStore` with its keys in the
Keychain and its pins in Application Support, the Moonlight manager over its
host store and the pinning gateway, and the hub over both) and the Bonjour
scan as its `LocalNetworkAccess`; the Moonlight identity is minted off the
main actor and handed to the manager and the gateway when it is ready. The
root wires the pool's signals to itself once (`wireNetwork`), so a refused
slot lets its binding go, a client that comes or goes moves the pads'
routes, and a satellite that wants a PIN opens its pairing card; and the
hosts' once (`wireMoonlight`), so a host's word reaches the page, its PIN
card follows the pairing, and a pool or records change moves the routes and
what each host is asked to carry.

`DishScene` is the composition root of the app layer. It makes `AppModel`,
`NavigationStore` and the intents' `IntentRouter` once: SwiftUI calls the
scene's initializer again on its own and keeps only the first build's state,
so the three live in an `OnFirstUse` holder kept as `@State`, made the first
time the kept build reads them. It hands the store the model's
`onboarding`, `startSetup` and `endSetup`, injects both with `.environment`,
passes down the two values only UIKit can give (`settingsURL`, from
`UIApplication.openSettingsURLString`, and `appVersion`, from the bundle),
hands the model the clipboard and the device's battery (which each pad's
battery is weighed against, `routeBattery` in `DishCore`),
drives `preferredColorScheme` from the appearance fact and sets the idle timer
from `idleTimerDisabled(facts:)`. It reads the device's idiom once
(`deviceIdiom(_:)`), for the orientation lock: an iPhone stands upright but
for play, an iPad follows the device on every screen. The same fact tells the
engine which device it is (`deviceKind(_:)` into `AppModel`'s `deviceKind`), so
a device with no name of its own introduces itself to the satellite as "iPhone"
or "iPad" (`wireDeviceName`); the words that name the device (about nineteen
catalog keys) are device variations in the String Catalog, which the OS picks. It puts `WindowReader`
(`Scene/WindowReader.swift`) at the window's root, the one reader of the
window's size classes and shape, which hands them down as `windowFacts`; the
iPad's layouts (the split tabs, the setup cover's column, the gamepad's
measures) are mappers over that fact. It is the one file that reads
`UIApplication.shared`, `UserDefaults.standard`, `UIDevice.current` and
`Bundle.main`; `NoSuppressionsTests` pins that, and `ViewPurityTests` does not
treat it or its seams under `Scene/` as views, and holds every other file to
reading no size class or idiom of its own (V13).

## Unidirectional flow: the rules

1. **One owner per piece of state.** It lives in exactly one source and is
   exposed read-only. Nobody else stores a copy. The setup walk lives in
   `AppModel`'s `setupSource`; the navigation state lives in `NavigationStore`.
2. **Derive, do not mutate.** Downstream values come from a pure transform: a
   mapper from facts to a view state.
3. **Effects as data, executed at the edge.** A reducer returns what to do; the
   model or the store does it. `reduceSetup` returns `SetupEffect`s that
   `AppModel+Setup` runs; `reduceNavigation` returns `NavigationEffect`s that
   `NavigationStore` runs.
4. **One publish, then rebuild.** The UI rebuilds from the snapshot; no
   per-field back channels that can miss a transition.
5. **Distinct-until-changed everywhere.** Every state value is `Equatable`,
   and `StateSource` drops an equal write.
6. **Commands flow the other way, explicitly.** The UI calls an intent on
   `AppModel`; the resulting state flows back out as a fact in `shellFacts`,
   which a page's mapper turns into its view state. A view holds no engine
   object: the scene hands its pages `AppModel` and `NavigationStore` and
   nothing else, and a page reaches everything through `ShellFacts`.
   `ViewPurityTests` enforces it, rule by rule
   ([UI_CONTRACT.md](UI_CONTRACT.md), "View purity").
7. **The engine vends data, the app vends words.** A fact is an enum or a
   number (`LinkHealth`, `ConnectionState.offline(lastSeen:)`, `DimDelay`);
   `L10n` is the one place a key becomes a word, and the String Catalog is the
   one place it is translated. The derivations between a fact and what a view
   draws (a row's text, a dot's colour, the "iPhone" a device name falls back
   to) are pure functions under `Sources/Dish/UI/Mappers`. A decision the fleet
   shares, such as the setup walk's, is a reducer in `DishCore`; the mapper
   only words its output. No `String` is built for display in `DishEngine`.
8. **A kit component reads no domain.** Anything under `Sources/Dish/UI/Kit`
   takes only its view state, tokens and closures; a host view beside the
   page maps the engine's value into that state and forwards the closures as
   intents. `ImportBoundariesTests` pins it: a kit file imports only SwiftUI
   and Foundation, observes no model and binds to none.
9. **Navigation is data.** `Sources/Dish/Navigation/NavigationMachine.swift` is
   a pure `reduceNavigation(state, event)` over the selected tab, each tab's
   pushed pages and the cover on screen; it returns its effects
   (`markWelcomeComplete`, `startSetup(entry)`, `endSetup`) as data and
   `NavigationStore` runs them and hands `TabView`, each `NavigationStack` and
   the `fullScreenCover` their bindings. See "Navigation" below.
10. **A page's lifecycle is an intent.** A page's `onAppear` and `onDisappear`
    forward `pageAppeared` and `pageDisappeared` to `AppModel`
    (`AppModel+Pages.swift`), which starts and stops what the page needs; today
    the Connections page runs the clock so an offline PC's "last seen" words
    stay current, and the view does nothing else there.

## Navigation

The machine is a pure function, `reduceNavigation(_:_:) -> NavigationStep`, over
`NavigationState` (the selected `Tab`, a `[Page]` per tab, the `Cover?`). Its
events and effects are the table in [UI_CONTRACT.md](UI_CONTRACT.md); the
shape is the dish-mac machine's, with the rail replaced by a tab bar and the
leave guard and the window gone.

- A tap on the tab already on screen pops it to its root, as iOS does.
- A page pushes onto the tab on screen; a pop the stack makes itself (the back
  button, a swipe) arrives as `pathChanged`, so the state follows the system.
- A tab's list opens one of its pages with `show(page, in: tab)`: the tab's
  path becomes that page alone. On a phone that is the push from the list;
  on an iPad, where Controllers and Connections draw the list beside the
  page, the first page of the path is the one beside the list (the list's
  selection) and the rest is that column's own stack, so a second row
  replaces the first rather than stacking on it.
- Setup and the dim are covers. Setup replaces whatever covered the tabs, the
  dim included; the dim rises only over the tabs, because the accessory that
  asks for it is not on screen under a cover.
- Leaving setup by any road, Skip, Bind or the system lowering the cover,
  lands on Controllers and completes the welcome, or it would rise again on the
  next launch. A cover the system lowers ends what it showed: setup as a skip,
  the dim as a wake.
- On a first run the store raises the setup cover before anything is drawn and
  starts the walk, so the tabs never flash.
- An App Intent is a navigation event, posted through the `IntentRouter` the
  scene registers with App Intents: the play screens and the dim are the
  accessory's own events, and Connect to a PC is `connectTo(id:)`, which shows
  the PC's page alone on Connections unless play or setup covers the tabs, and
  hands the model the connect as an effect.
- After each event the store tells TipKit which hint the person no longer
  needs (`learnedHint(_:from:to:)`), so the hints are put to rest as data too.

`NavigationCoverageTests` keeps the map whole: every `Tab` and `Page` case has
its worded title in `ShellMappers.swift`, its `<Name>Page.swift`, its
`<Name>MappersTests.swift` and a branch of the shell's switch, and every
`Cover` case has its `<Name>Cover.swift` and a branch of the cover switch.

## The setup machine

The setup walk is `reduceSetup(state, event, localNetwork:)` in `DishCore`: a
pure function from a `SetupState` (the step, the draft, where the walk opened)
and a `SetupEvent` to the next state and a list of `SetupEffect`s. It is in the
core, not the engine, because it is a decision with no IO, and it is tested
there (`Tests/DishCoreTests/SetupMachineTests.swift`) with no mocks.

- The steps are `welcome`, `input`, `localNetworkPrimer`, `pickPC` and
  `review`. The primer and Pick your PC are both the Destination step: the
  primer stands in while the Local Network status is `.unknown`, and its
  Continue emits `.askLocalNetwork`; the answer moves to Pick your PC and emits
  `.scan` when allowed. iOS puts the question only once, so an earlier answer
  is the answer.
- The primer being asked (`.askLocalNetwork`, or the `.scan` that follows an
  answer) marks it seen under `local_network_primed`, dish-mac's key, and so
  does the person's own scan (`startScan`). The Connections tab's opening scan
  (`pageAppeared(.connections)`) runs only once that flag is set, so iOS asks
  its question after the explanation and not as the tab first opens.
- A pick of the input moves on and seeds the draft (a seen pad emulates its own
  family, anything else an Xbox Wireless; motion follows what the pad carries).
- Review's Bind emits `.bind(draft)` then `.ended(.bound)`. Skip anywhere emits
  `.ended(.skipped)`. Back walks one step; there is none from the welcome, and
  none from Input when the walk opened there ("Add a controller").
- Nothing leaves the draft until Bind. Bind of a pad iOS sees, or of the
  on-screen gamepad, to the satellite the walk picked or the one added by
  address (`AppModel.addedByAddress`) writes the pick and the motion switch
  and binds it (`bind(slotId:to:)`), which rides the session PUT, or the
  per-slot PUT while live; the wired and Bluetooth ways in have no pad to
  bind yet, and a Moonlight host no satellite.

`AppModel+Setup` applies the machine to the model's `setupSource` and runs the
effects: `.askLocalNetwork` runs the first browse, which makes iOS put its
question, and answers the walk when the status leaves unknown; `.scan` goes
to the `LocalNetworkAccess` seam; `.bind` binds; and `.ended` is the view's
business (the cover
sends `navigation.send(.setupEnded(...))` itself, and the model only drops the
walk when `endSetup()` is called). The pure view-layer half is
`setupCoverState(facts:words:)` and the step mappers.

## Threading and the hot path

The hot path is built end to end. `GameControllerInput` hands each pad its own
serial `handlerQueue` before installing a handler; the handler samples the
extended gamepad into a `PadSample`, `wireReport` turns it into a
`GamepadReport`, and the pad's `PadFeed` drops a report that repeats the last
one, applies the dead zones from an atomic word, writes the inspector's
record under a seqlock and calls the `PadSink` of the route it took from its
mailbox. The feed is `Sendable` because every field is an atomic word or a
`let`, not because anything is promised past the compiler. A bound pad's
route holds the satellite's live `SatelliteClient` as its sink and the index
the pad holds there: `AppModel+Binding` publishes one routing snapshot from
the bindings and the live clients through `InputRouting` whenever a binding,
a client or a switch changes, so a pad's route is set when its satellite's
session comes up and cleared when it goes down. The client stamps nothing of
its own: the feed hands it each motion sample's delta since the last one let
through and each touch's publish instant, as the wire carries them.
`SatelliteClient.send` claims the counter, seals the report from a stack
buffer and calls `sendto` while it holds the send gate, a compare-exchange
flag; the generation it seals under, the target and the fd are atomic words
and an object slot replaced only under that gate, so the send takes no lock
and allocates nothing but CryptoKit's sealed box, on the pad's own queue.

The receive loop runs on a thread of its own at `userInteractive`
(`ThreadRole.receive`), with one datagram buffer on its stack: it opens each
datagram in place, takes each new key generation and handler set from a
mailbox, and hands a rumble, light-bar, trigger or player-LED command to the
connection's `FeedbackRoutes`, which post it to the bound pad's feedback in
one hop. The heartbeat runs on its own queue (`ThreadRole.heartbeat`) and
takes the latency window's lock to arm its ping; the receive loop only leaves
an ack's time in an atomic word for the next holder to pair. The return paths
post to each pad's `FeedbackPad`, and `PadActuators`, an actor whose executor
is the `dish.feedback` queue, drives CoreHaptics, the light, the adaptive
triggers and the player index; a `GCController` is filed there by identity
and found in the framework's own list, so it never crosses isolations.
`LockLawTests`, in a `LOCK_STATS` build (its own CI job), holds the Input,
Receive and Feedback threads to no tracked lock and the Heartbeat to the
latency window's alone, over a pad routed to a live client and a loopback
satellite answering it. Everything else in the engine is `@MainActor`.

A pad bound to a Moonlight host routes to a `MoonlightPadSink`: the host's
`MoonlightPadLink` builds the frame under its lock (the pad table, the click's
replay, the touches, motion and battery) and hands it to the
`MoonlightControlSession`, which seals it under the next control sequence,
claimed atomically, before it takes its own lock for the ENet bookkeeping
alone; the datagram leaves through `UdpControlTransport`, whose send counts
its datagrams in flight in atomic words. The control socket's queue
(`ThreadRole.moonlightUdp`) acknowledges the host under the session's lock,
opens the host's events after it, and posts rumble and light through
`MoonlightFeedbackRouter` to the pad's feedback, the routes the main actor
last built read under a lock of their own; the session's clock ticks on a
`ThreadRole.heartbeat` queue. `LockLawTests` holds that path to its own lists,
from a run against a loopback host: Input to the link's and the session's
locks, MoonlightUdp to the session's, the link's (a motion request) and the
feedback path's three, Heartbeat to the session's; nothing held across a
blocking call, nothing nested. dish-mac's path also takes its transport's
lock, which is atomic words here, and its forwarding gate and routing table,
whose part the router's own routes play here.

These are the rules the bridge and the wire keep, taken from dish-mac:

- Every controller event takes one path and takes no lock on it. A
  controller's handler runs on that controller's own serial queue, its
  `handlerQueue`, set before any handler is installed, so no event waits
  behind the main thread or another pad.
- On that path: no lock, no allocation, no main-actor hop, no `Task`, no
  `await`, no Observation. The report is sealed from a stack buffer and
  leaves through `sendto`, on a raw POSIX socket carrying `IP_TOS = 0xB8`
  (DSCP EF) and `SO_NOSIGPIPE`.
- The kernel is never on that path. `StateSource` is for state the UI reads;
  what the hot path shares with the main actor travels in atomic words and
  mailboxes.
- The main actor owns every published property. Handler installs are
  `nonisolated`, so the compiler refuses a handler that reaches for
  main-actor state.
- Return paths (rumble, the light bar) run the other way in one hop to a queue
  that owns the actuators.
- A mailbox or a direct send before a queue. The siblings carry a lock-free
  bounded queue of Vyukov's design (the satellite's log queue, the desktops'
  `MpscQueue` under the speaker playout, Android's `mpmc_ring` under the
  bridge, the speaker and the USB acks); dish-mac carries none, and neither
  does this client: no lane here has several producers feeding one consumer,
  and iOS has no pad speaker and no USB output lane without the Direct path.
  `Tests/PARITY.md` says when one would be ported and in which form.
- Some of the siblings' capabilities sit behind entitlements Apple grants on
  request: the multicast entitlement for the legacy discovery beacon, raw HID
  access for the Direct path. The hot path reaches every pad through
  GameController and every satellite through Bonjour until they are granted;
  `Tests/PARITY.md` lists them.

## How to add a feature

1. **Name the state.** A lifecycle takes a reducer in `DishCore` with an
   exhaustive test; a setting takes a store.
2. **Write the pure core first**, red then green, in `DishCore` or as a free
   function. No IO.
3. **Own it in a store** in the engine that holds a `StateSource`, or a
   coordinator method for a cross-cutting command. Feed world signals in;
   expose state out. A platform capability goes behind a protocol seam, with
   a recording or manual implementation for tests.
4. **Project it in `AppModel`** as a field of `ShellFacts` plus the intents,
   and build every state of the page: empty, loading, error and content, each
   through its mapper and shown in a `#Preview`.
5. **Localize at the edge.** A new word is an `L10n` property with its catalog
   entry and five translations; the engine gets a case, not a sentence, and the
   view gets the property, not a literal.
6. **Wire it once in `AppModel`**, the only composition root, and update
   [`../Tests/PARITY.md`](../Tests/PARITY.md) in the same change.

## Known limitations and not yet implemented

Each entry names the decided shape, so a change lands on it. The row-by-row
list, with where each lands, is [`../Tests/PARITY.md`](../Tests/PARITY.md).

- **A PC added by address is listed only once paired.** The pool reaches
  for it and its pairing card opens, but the Connections tab's rows are the
  remembered and the heard satellites, so a cancelled pairing leaves no row.
- **A Moonlight host carries input only.** The session asks the host for no
  video or audio: the control stream carries the pads, and the media pings
  only keep the host's ports open, as dish-mac's do.
- **A binding is remembered and restored.** `AppModel+BindingMemory` watches
  the pads, the pool, the satellites and hosts on record and the on-screen
  gamepad's listing with Observation and binds each remembered binding whose
  pad is present and whose destination is known, once while the pad stays
  attached. The pad's pick is the pad's own (`emulated_type_preferences`)
  for a satellite and the record's type for a host, which the desire reads
  (`MoonlightDesire.desiredPads(bindingTypes:)`).
- **The pair sheet's countdown is the poll's clock.** The approval poll adds
  its interval to the attempt's `elapsedMs` (`PairingAttempts.advance`) before
  it reads the reply, so the sheet's "Waiting · 1:58" is the time the
  satellite still keeps the request, never a timer of the sheet's own.
- **The controller page reads the Diagnostics source.** `pageAppeared(.controller)`
  starts the same 1 Hz tick the Diagnostics page uses, so the Gamepad, Motion
  and Touch rates are the `InputRateTracker` readings over the pads' record
  counts (`PadRecord` counts a pad's reports, admitted motion samples and
  touchpad samples in words of their own, outside the seqlock).
- **The Local Network status is the last scan's word.** iOS has no call that
  asks; the simulator does not enforce the permission, so the denied path is
  proved through the browser's documented policy error, not observed
  (`LocalNetworkProbeTests`).
- **iOS gives apps no pad speaker.** The Review step's "Gets back" column
  never carries a speaker, because iOS offers apps no way to play into a
  controller.
- **A custom satellite glyph is not drawn.** An SF Symbol antenna stands in.

## Testing

- **The pure core is the contract.** The setup machine has a test for every
  step, event and branch, in `Tests/DishCoreTests`, with no mocks.
- **The kernel is tested as a kernel.** `Tests/DishKernelTests` pins
  `StateSource`'s distinct-until-changed rule.
- **The engine is tested against fakes it owns.** `Tests/DishEngineTests`
  drives the stores over a fresh `UserDefaults` (`TestDefaults`), the clock
  over a `ManualTicker`, the pads over `FakeControllerSource`, and the network
  against `FakeSatellite`, an in-process satellite on the loopback with its
  own crypto; the model's intents run over a scripted LAN and an in-memory
  key store. The Moonlight manager runs over a scripted gateway and session
  edges, and `IntegrationMoonlightFakeHostTests` drives it over the real
  sockets against `FakeMoonlightHost`, a loopback host that pairs, answers
  over mutual TLS with a PKCS#12 identity, hands out its RTSP ports and opens
  every sealed control packet. `IntegrationLiveSatelliteE2ETests`, gated on `DISH_E2E_LIVE=1`,
  drives the real satellite binary through `scripts/e2e_local.sh` and
  `e2e.yml`.
- **The rules are tested.** `Tests/ArchitectureTests` reads the tree: import
  boundaries, the dependency graph, license headers, suppressions, mutable
  statics, the lint thresholds, the tool and workflow pins, the version
  mirrors, the catalog, the tokens, the view purity rules (`ViewPurityTests`)
  and the navigation's coverage (`NavigationCoverageTests`).
- **The app layer is tested where it decides.** `Tests/DishTests/Mappers`
  covers every page's mapper, one test per flow (empty, content, each
  variant, an iPad's included), `Tests/DishTests/Navigation` covers the
  machine, the store and the orientation per device, and
  `Tests/DishTests/Scene` the scene's facts: the idiom, the lock's answer,
  the window's size classes and shape, and the device's battery as UIKit
  reports it. What a test cannot say, how it
  looks, is a `#Preview` per state, the iPad's on its side and upright
  among them; the UI tests run on an iPhone and again on an iPad.
