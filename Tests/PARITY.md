# Parity: dish-ios against the other Dish clients

> **What this is.** The feature-parity ledger for this client, kept as a small
> matrix. **A pull request that changes a row updates this file in the same
> change**, and a reviewer checks the row. Coverage is not mapped here: the
> suites under `Tests/` are the coverage truth and CI runs them on every push.
> Deferred work lives here, never in a `TODO` comment.
>
> Legend: **built** works as the row says · **mapper only** the state is built
> and tested through its mapper and shown in a `#Preview`, but nothing reaches
> it at run time yet · **not yet** not built; the row says where it lands ·
> **n/a** does not apply on iOS · **not possible** iOS gives an app no way to
> do it; the row says why. Verified against the code on 2026-11-11.
>
> Wave 1 built the shell; wave A the protocol core; wave B the controller
> bridge; wave C the network engine; wave E the play screens; wave F the
> Moonlight hosts; wave G1 Support Dish, Help & FAQ, the licenses and the
> About links; wave G2 Diagnostics; wave D the pair sheet, the Connections
> rows, the PC's page, the controller page's Binding and Add a PC by address;
> wave H the iPad; wave G3 the rows' long-press menus and swipes, pull to
> refresh, App Intents and the TipKit hints; wave P1 the parity sweep
> (bindings that survive a restart, the motion word, Moonlight in Diagnostics,
> the host's Emulate picker); wave P2 the second parity sweep (the controller
> page's telemetry, the Dead zones page and the global switches, the pair
> sheet's countdown, a PC added by address listed before it is paired, the
> Connections scan after the primer, an iPad's words). A Satellite or a Moonlight host is found, paired
> with, bound to a pad or the on-screen gamepad and streamed to, from the app
> alone, on an iPhone or an iPad.

## 3. Permission-gated APIs the later waves need

Apple grants these on request, so each wave that needs one asks early and
ships without it until it is granted; the code keeps the feature behind a seam
so the sanctioned path works alone.

| Capability | What needs it | Until it is granted |
|---|---|---|
| `com.apple.developer.networking.multicast` | Listening for the satellite's legacy UDP discovery beacon on 9879, or any broadcast or multicast send. Browsing `_satellite._udp` and `_nvstream._tcp` over Bonjour needs no entitlement, only the `NSLocalNetworkUsageDescription` and `NSBonjourServices` the Info.plist already carries. | Discovery is Bonjour only; the beacon fallback stays off and `docs/contract.md` says so. |
| Raw HID report access for the Direct path | Reading Switch Pro, N64 and generic HID pads by their reports, as dish-mac does with IOHIDManager and the desktops with their own readers. iOS has no public HID report API for an app: DriverKit with its USB transport entitlement exists on iPadOS only, and CoreHID is macOS only. | Every pad reaches the hot path through GameController alone; the Direct path and its USB output lane wait behind their own seam, and the entitlement request is made before that wave starts. |

## 4. Decided differences

- **Pull to refresh on an iPad becomes Scan.** iPadOS 26 does not let a pull
  reach `.refreshable` in a `NavigationSplitView`'s list column (a probe
  counted no refresh, with the scroll view always bouncing and with the
  refresh on the scroll view itself), so on an iPad the Connections column's
  toolbar offers Scan beside Add, which runs the same scan; the phone keeps
  the pull. `ConnectionsUITests` covers each.
- **Appearance defaults to the system's, not dark.** The design handoff calls
  dark "the default" palette; the Settings › Appearance picker (System, Light,
  Dark) stores dish-mac's `ThemeMode` raw values under `theme_mode`, and a
  fresh install follows the system, as dish-mac does. The dark tokens are the
  design's; only the default differs.
- **iOS 26 only.** The design handoff describes an iOS 18 fallback for the tab
  bar and the accessory. This client has none: no `if #available`, no custom
  session bar.
- **An iPad's play cover follows the device.** On an iPhone the play cover
  turns the window to landscape. iPadOS 26 turns the window of an app that
  shares the screen with the device, whatever the app's mask says, and
  refuses it a programmatic turn (`UISceneErrorDomain` 101, "The current
  windowing mode does not allow for programmatic changes to interface
  orientation"); `UIRequiresFullScreen`, deprecated in iPadOS 26, only shrinks
  a landscape window into a letterboxed one over the Home Screen. So an
  iPad's play cover opens the way the iPad is held, and upright the gamepad
  keeps its landscape arrangement along the bottom (`padLayout`).
- **The iPad's tabs open as a bar along the top.** `sidebarAdaptable` on
  iPadOS 26 draws the three tabs as a bar along the top that opens into a
  sidebar; opening the sidebar by default
  (`defaultAdaptableTabBarPlacement(.sidebar)`) would lay it over the content
  on an upright iPad, where the first tap only closes it, and three tabs do
  not need a column of their own.
- **One red for errors.** The design leaves a choice between `#FF6B5C` and
  `#E74C3C`; the code uses `#FF6B5C` in the dark palette
  (`DishTheme.error`).
- **Tips are App Store purchases, and no donation link is in the app.** The
  desktops' and dish-mac's Support page links GitHub Sponsors, Ko-fi and Buy
  Me a Coffee; Apple requires in-app purchase for tips in an iOS app, so Dish
  for iOS sells three consumable tips through StoreKit instead and links none
  of those sites (`DishLinksTests` pins that). Help & FAQ answers "What do
  tips pay for?" in their place.
- **Help & FAQ answers for an iPhone.** The desktops' answers that speak of a
  tray, a window, two PCs or Settings › Diagnostics are reworded: pads pair
  in Settings › Bluetooth, iOS asks for the Local Network once, a Dish you
  leave is suspended (so it dims instead), and there is no crash reporting to
  turn off.
- **iOS gives apps no pad speaker.** The Review step's Gets back column never
  carries a speaker.
- **A backgrounded Dish does not stream.** iOS suspends Dish when it leaves the
  foreground, so Keep screen on holds the idle timer off while a session is up
  and the dim exists to save power; nothing keeps the app running in the
  background, and no Live Activity is used (the design says so).
- **No `PadGate`, no profile path, no Direct reader.** dish-mac's gate picks,
  per pad, whether GameController or its Direct HID reader is published, and
  its profile path reads pads GameController vends without the extended
  profile. iOS has neither HID access nor a second source, so nothing would
  read the gate: a pad's feed publishes every change, and a pad without the
  extended profile is listed as "Not supported" and left alone.
- **The return path's commands arrive as fields.** `FeedbackRoutes` takes the
  rumble, light-bar, trigger and player-LED values the receive loop decoded
  rather than dish-mac's `RumbleCommand`-shaped values, so the controller
  bridge needs nothing from the wire codecs.

## 5. Pads and return paths, as iOS allows them

What reaches a pad through GameController, and the pads iOS keeps from an
app. Checked on 2026-11-11 against the code here, GameController's API and
SDL's sources (`SDL_hidapi_steam.c`, `SDL_hidapi_steam_triton.c` and the iOS
backend `src/hidapi/ios/hid.m`, all zlib); none of it has been tried on
hardware yet.

| Pad or path | Status | How, or why not |
|---|---|---|
| **A DualSense's rumble, adaptive triggers, light bar and player LEDs from a satellite** | built | Each command arrives on the receive loop, passes the pad's switch (the light bar the global one too) and lands on the pad's feedback record; the feedback queue plays the newest of each kind through GameController. MSG_RUMBLE drives two `CHHapticEngine`s from `GCController.haptics`, the strong motor at `.leftHandle` and the weak at `.rightHandle`; MSG_TRIGGER_EFFECTS is decoded from the firmware's 11-byte blocks (`DualSenseTriggerEffect`) onto `GCDualSenseAdaptiveTrigger`'s off, feedback, weapon and vibration modes and their ten-zone forms; MSG_LIGHTBAR is `GCDeviceLight.color`; MSG_PLAYER_LEDS is `GCController.playerIndex`. What the API cannot say: the galloping effect plays as off, the machine effect as a ten-zone vibration at its first amplitude with no period, the bow as a weapon; the LEDs show the framework's four player patterns rather than any mask; and an app gets no haptic audio, speaker or microphone on the pad. A black light bar the satellite writes is painted black here: the satellite's DualSense output decoder is where that is fixed. |
| **An 8BitDo Ultimate 2 Wireless in X-input mode** (USB 2DC8:310B, the Xbox 360 wired protocol) | not possible | X-input mode is a vendor-class USB interface, not HID, and GameController drives no Xbox 360 pad, so iOS vends no controller for it; an app gets no USB or HID access to read it itself (section 3). On an iPad with an M-series chip, a DriverKit driver Apple entitles for the vendor's USB devices could claim the interface; Dish has none. |
| **A Steam Controller (2015) on USB or its wireless dongle** (28DE:1102, 28DE:1142) | not possible | The pad's interface is vendor HID, and lizard mode is turned off by feature reports (SDL clears the digital mappings and sets both trackpads to none); iOS lets an app do neither, and GameController does not vend the pad, so iOS sees only lizard mode's keyboard and mouse. |
| **A Steam Controller (2026) on USB or its dongles** (28DE:1302; the Proteus and Nereid dongles, 28DE:1304 and 28DE:1305, one pad per interface 2 to 5) | not possible | The same: vendor HID reports, and a lizard-mode setting the firmware's watchdog restores unless it is sent again every 3 s, neither reachable from an app. |
| **Either Steam Controller on Bluetooth LE** (the 2015 pad on its BLE firmware, 28DE:1106; the 2026 pad, 28DE:1303) | not yet | GameController does not vend them, but CoreBluetooth reaches them. SDL's iOS backend talks to Valve's GATT service `100F6C32-1735-4313-B402-38567131E5F3`: the 2015 pad's input on `100F6C33-…`, the 2026 pad's reports 0x45 and 0x47 on `100F6C7A-…` and `100F6C7C-…`, the feature reports on `100F6C34-…`, through which its drivers turn lizard mode off and over which they decode `ID_CONTROLLER_BLE_STATE` and `ID_TRITON_CONTROLLER_STATE_BLE`. A port is a source beside GameController in the engine, with `NSBluetoothAlwaysUsageDescription` and the Bluetooth question it brings (SDL keeps the driver off by default on iOS for that reason), and a pad of each kind to verify it on. |
